# 音视频通话二期：通话记录展示 - 前端技术方案

## 一、需求分析

### 1.1 需求背景与目标

一期已实现通话界面（CallView / IncomingCallModal / CallingView），但通话结束后聊天记录中无痕迹。本期将通话记录作为一种系统消息类型（`msg_type=6`）在消息流中展示，与文字/图片消息按时间序混合排列。

### 1.2 现状分析

| 环节 | 现状 | 可复用/缺失 |
|------|------|-------------|
| `MSG_TYPE_CALL_RECORD = 6` | `messageModel.ts:9` 已定义常量 | **可复用** |
| `messageDisplayText` | type=6 返回 `'[通话记录]'` | **可复用**，会话列表摘要已覆盖 |
| `isSystemMessage` | 仅匹配 type=5 和 3 | **不包含** type=6，需独立判断 |
| `normalizePushMessage` | 正确解析所有 msg_type，含 type=6 | **可复用**，无需改动 |
| `realtimeModel` | `applyIncomingMessage` 处理所有新消息 | **可复用**，type=6 走相同流程 |
| `MessageBubble` | 无 type=6 专属渲染，走通用文本气泡 | **需新增**卡片渲染 |
| call 类型定义 | `CallEndReason` 已定义 | **可复用** |

### 1.3 核心约束

1. 通话记录仅展示为卡片，不可撤回、不可回复、不可转发（渲染层约束，后端不限制）
2. content 为结构化 JSON，前端解析渲染
3. 区分"已接通"（展示时长）和"未接通"（展示结束原因）两种样式

## 二、系统概要设计

### 2.1 组件架构

通话记录卡片在 `MessageBubble` 中渲染，层级如下：

```
MessageList
  └── MessageBubble
        ├── msg_type=1/2 → 文字/图片气泡（现有）
        ├── msg_type=5/3 → 系统消息 pill（现有）
        ├── msg_type=6 → 通话记录卡片（新增 CallRecordCard）
        └── revoked     → 撤回提示（现有）
```

### 2.2 数据流

```
WS message/new (msg_type=6)
  → RealtimeClient.onmessage
  → normalizePushMessage → MessageDTO { msg_type: 6, content: JSON }
  → applyIncomingMessage → message list
  → MessageBubble 渲染
    → isCallRecord(msg) → true
    → parseCallRecordContent(msg.content) → { call_type, duration, end_reason, status }
    → CallRecordCard 组件
```

### 2.3 状态管理

不新增状态。通话记录卡片是纯展示组件，数据全部来自 `MessageDTO`。

## 三、系统详细设计

### 3.1 组件设计

#### CallRecordCard（MessageBubble 内联函数）

渲染为居中卡片样式，与现有系统消息 pill 视觉层级一致但样式不同：

```
┌────────────────────────────────┐
│  📞 语音通话  05:30            │  ← 已接通：图标 + 类型 + 时长（蓝色）
│  📹 视频通话  已拒绝            │  ← 未接通：图标 + 类型 + 原因（灰色）
└────────────────────────────────┘
```

| 状态 | 展示内容 | 图标 | 文字颜色 |
|------|---------|------|---------|
| 语音-已接通 | 语音通话 + MM:SS | 📞 电话 | `#4080e0` |
| 视频-已接通 | 视频通话 + MM:SS | 📹 视频 | `#4080e0` |
| 语音-未接通 | 语音通话 + 原因文本 | 📞 电话 | `#9aa1ad` |
| 视频-未接通 | 视频通话 + 原因文本 | 📹 视频 | `#9aa1ad` |

结束原因映射：
- `hangup` / `rejected` → "已拒绝"
- `timeout` → "无人接听"
- `cancelled` → "已取消"
- `disconnect` → "连接断开"

### 3.2 Hook 设计

#### messageModel 新增方法

```tsx
// 判断是否为通话记录消息
export function isCallRecord(msg: MessageDTO): boolean {
  return msg.msg_type === MSG_TYPE_CALL_RECORD;
}

// 解析通话记录 content JSON
interface CallRecordContent {
  call_id: string;
  call_type: 1 | 2;
  duration: number;
  end_reason: string;
  status: 1 | 2;  // 1=missed, 2=completed
}

export function parseCallRecordContent(content: string): CallRecordContent | null;

// 生成通话记录展示文案
export function callRecordLabel(callType: 1 | 2, status: 1 | 2): string;

// 结束原因中文文案
export function endReasonText(reason: string): string;

// 时长格式化 MM:SS
export function formatDuration(seconds: number): string;  // 已在 callModel.ts，复用
```

### 3.3 WS 协议

无需新增上行。

下行 `message/new`（msg_type=6）数据格式：

```json
{
    "type": "message",
    "action": "new",
    "data": {
        "message_id": 123,
        "conversation_id": 1,
        "seq": 10,
        "sender_id": 0,
        "msg_type": 6,
        "content": "{\"call_id\":\"call_xxx\",\"call_type\":1,\"duration\":120,\"end_reason\":\"hangup\",\"status\":2}",
        "created_at": 1700000000
    }
}
```

前端解析流程（realtimeModel 中无需改动，`normalizePushMessage` + `applyIncomingMessage` 已正确处理 type=6）：

```
msg.type === 'message' && msg.action === 'new'
  → normalizePushMessage(msg.data) → MessageDTO { msg_type: 6, content: JSON }
  → applyIncomingMessage(message) → 插入 messages store
```

### 3.4 类型定义

`api/types.ts` 无需新增。通话记录 JSON 的解析类型定义在 `messageModel.ts` 中即可。

### 3.5 会话列表摘要

`messageDisplayText` 在 type=6 时已返回 `'[通话记录]'`，需优化为更具体的摘要：

| 状态 | 摘要示例 |
|------|---------|
| 语音-已接通 | `[语音通话] 05:30` |
| 视频-已接通 | `[视频通话] 02:00` |
| 语音-未接通 | `[语音通话] 已拒绝` |
| 视频-未接通 | `[视频通话] 无人接听` |
